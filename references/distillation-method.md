# 蒸馏方法详述

六类可复用配方（问答／SOP／推理链／人设／示例／多源融合）+ 两类支撑机制（迭代蒸馏、标准表示与质量度量）+ 一路分流策略（RAG 路由）+ 一维纵向层级树框架（道法术器双向蒸馏：道⊃法⊃术⊃器⊃细节）+ 领域扩展与预设（domain_ext）+ 跨次续抽合并（Incremental Merge）+ 可选抽取维度（触达/条件/验收/契约/推理树/生命周期/治理扩展桶）+ 媒体摄入协议（视频/网址/多次收集，第17节）+ 记忆与双层进化（第18节）。按知识类型选用，按需组合。目标始终是压缩 + 泛化，绝不逐字抄写。

## 1. 问答蒸馏（Q&A）
适用：FAQ、支持记录、知识库文章。
- 把每条问答转成紧凑规则或原则，而非复制成对。
- 聚类相似问题；保留一个规范答案加其变体。
- 捕捉"触发词"（用户哪些说法映射到该答案）。

## 2. SOP / 决策树蒸馏
适用：流程、清单、运维手册。
- 提取步骤顺序与每个分支的条件。
- 表示为 条件 → 动作；给出兜底。
- 注明每步所需输入/工具。

## 3. 推理链蒸馏（CoT）
适用：专家判断、排障、分析。
- 不只给结论，捕捉推理链。
- 把专家的"怎么想"编码为显式子步骤。
- 比只给结论的提示质量高得多。

## 4. 人设蒸馏（Persona）
适用：语气敏感或品牌语调任务。
- 从样本中提炼语气、边界、禁忌、升级规则。
- 编码为系统提示中的身份 + 约束。

## 5. 示例蒸馏（Few-Shot）
适用：任何需要一致格式/风格的任务。
- 生成 2–4 个高质量 输入 → 输出 对。
- 配对须展示"思考方式"，而非仅正确标签。
- 这些成为技能的 examples 块。

## 6. 多源融合蒸馏（Multi-Source Fusion）
适用：把多本书 / 多份文档 / 一个知识库蒸馏成**一个**技能。
- 每个来源先解析为文本（本地→解析；在线知识库→连接器检索）。
- 逐源独立抽取，再对齐：去重、消歧、冲突裁决、溯源。
- 压缩为跨来源成立的原则；仅把单源特有内容作边界 case。
- 按统一能力命名，而非按某个来源。
- 在线知识库前提：连接器须先连接并授权，方可检索。

## 压缩规则
- 去冗余；每条规则一种规范表述。
- 显式消解冲突；说明所作假设。
- 只保留可泛化的；除非是边界 case，否则丢弃一次性细节。
- 始终保留示例，让模型一秒进入角色。

## 反模式
- 大段照搬原文（违背初衷，膨胀技能）。
- 隐藏矛盾而非消解。
- 编造来源不支持的知识。
- 跳过 few-shot 示例（质量骤降）。

## 7. 迭代蒸馏（Iterative Distillation）
适用：一切追求高保真的蒸馏；尤其是专家判断、多步骤流程、易出幻觉的领域。
- 不依赖模型「脑中自检」。把草稿技能实际加载到子 Agent／沙箱，用从来源抽取的 gold 测试集实跑。
- 逐条比对输出与金标准，把失败 case 回传到「压缩」步重提炼；必要时回到「抽取」补信息。
- 设定通过率门槛（默认 ≥80%）与迭代上限（默认 3 轮），达标即停，否则保留残留盲区清单。
- 让蒸馏从单次线性变成「生成 → 验证 → 修正」闭环，显著提升首版可用性。

## 8. 标准表示与质量度量（Standard Representation & Metrics）
适用：一切蒸馏；尤其是要规模化、要批量比对、要交给人工审阅的场合。
- **统一中间表示**：抽取一律输出固定 JSON Schema（v3.0），字段为 11 横向桶（`entities/relations/rules/decisions/metrics/qa/examples/steps/persona/edge_cases/ambiguity`）+ 结构/层级/导图/流通桶（`structure/dftq/flows/mindmap`）+ 领域桶（`domain_ext`）+ 可选扩展桶（`triggers/conditions/state_machine/acceptance/io_contract/decision_tree/diagnosis/freshness/deps/permissions`）+ 媒体元数据桶（`source_media`），每项带 `dim`（道法术器/detail/cross）、`path`（章节锚点）、`confidence`（high/medium/low）与 `source_ref`。统一结构让跨批次、跨来源的产物可比、可聚合。
- **覆盖率（Coverage）**：压缩后以抽取项为基线，估算「来源要点 → 技能」的进入比例；统计 pending ambiguity 数与 low-confidence 项的处理方式（保留/降级检索/需人工）。低于阈值（默认 <70%）回流补抽取或升级路由 B。
- **置信度（Confidence）**：每个抽取项标 high/medium/low；low 与 ambiguous 项排到「待人工审阅优先级」最前，让人工把关聚焦最高风险内容。绝不把 low 项默默当真。
- **价值**：质量不再是「感觉还行」，而是一组可度量、可排序、可解释的数字——既判断是否够好，也决定人工审阅先看哪。

## 9. RAG 路由分流（RAG Routing）
适用：来源过大（多册书、整库、海量文档）或频繁变动（每周/每月更新）的蒸馏。
- 第 1 步做「体量 × 动态性」评估，命中即走**路由 B**而非把知识全塞进 SKILL.md：
  - **骨架技能**：只含稳定不变的部分——能力定位、判断流程、输出模板、调用约定；
  - **检索路由**：写明「凡涉及来源细节/事实，先去 `<知识库名/id>` 检索再作答」，并把名称/id 记入 references/；
  - **索引约定**：告诉调用方如何检索（关键词、检索范围、是否需授权）。
- 核心原则「骨架稳定、细节外挂」：避免 SKILL.md 膨胀撑爆上下文，也避免知识随源更新而过期。前提是来源可被检索——本地导出索引，或已连接在线知识库；若两者皆无，先提示用户补齐检索后端。
- 与路由 A（全量嵌入 Stable, Compact）互斥选择：小且稳定 → A；大或常变 → B。

## 10. 冲突裁决细化（Conflict Resolution Refinement）
适用：多源/知识库蒸馏中来源相互矛盾，或某来源内部自相矛盾的情形。
- **权威等级表**：先按来源权威分级（官方规范 > 公司 SOP > 行业手册 > 社区经验 > 单篇博客），同级再用更新度（最近修订时间）破平。避免「两本同等权威的书无从下手」。
- **置信加权**：带入第 2 步抽取的 `confidence`；高权威且高置信者优先，规则旁注明「置信：来源X(high) / 来源Y(medium)」。
- **分歧显式标注**：选中的规则与落败的备选都写进产物（「采用 A；备选 B，理由…」），确保可回溯、可纠错——绝不悄悄丢弃落败方。
- **「需人工确认」标记**：当权威同级、置信冲突、或涉及合规/安全红线时，在 `ambiguity` 标 `resolution: "needs_human"`，并在残留盲区列明，绝不自行定夺。
- 每条冲突产出「冲突点 / 采用 / 舍弃 / 理由」四元组，汇入溯源说明，让后续重蒸馏或人工审阅可一键定位。

## 11. 道法术器层级树蒸馏（Dao-Fa-Shu-Qi Hierarchical Distillation）
适用：任何希望技能「既有可操作细节、又有原则锚定」的知识——尤其方法论、培训材料、专家心法、成事/修身类内容。它补上标准 Schema 缺失的**纵向层级**，与横向五层正交，构成完整抽取矩阵。

- **层级嵌套定义（纵向 5 层树，非并列四列）**：
  - **道 ⊃ 法 ⊃ 术 ⊃ 器 ⊃ 细节** —— 很多条「道」→ 每条道下很多「法」→ 每条法下很多「术」→ 每条术下很多「器」→ 每个器下很多「细节」。每层子项数**不设硬上限**。
  - **道**：原理、宗旨、价值观、本质规律、底线——回答"为什么这么做""什么绝对不能做"。落到子技能 = 核心原则 / 禁止清单。
  - **法**：方法论、框架、规则、决策逻辑——回答"用哪套方法/什么约束"。落到子技能 = 规则 / 决策树。一条道下可挂多条法。
  - **术**：具体步骤、技巧、话术、窍门——回答"具体怎么做"。落到子技能 = 工作流步骤 / few-shot。一条法下可挂多条术。
  - **器**：工具、系统、模板、术语、指标——回答"用什么干"。落到子技能 = 工具表 / 术语表 / 量化阈值。一条术下可挂多条器。
  - **细节（detail）**：参数、字段、模板正文、边界值——回答"具体填什么/怎么配"。一条器下可挂很多细节。
  - **cross**：跨层关系、流程衔接点。
- **层级树载体（dftq 桶）**：每条节点 `{id, parent_id, dim, title, summary, detail, confidence, source_ref}`，`parent_id` 指向上一层，形成归属链。横向桶（rules/steps/…）可附 `dftq_ref` 挂接。这是子技能的**主结构来源**，而非平铺四列标签。
- **自动判断缺失层与断链**：不是每份资料都全含五层（如纯操作手册可能只有"术+器+细节"），也不保证每层都满链。第 2 步末尾做「五层覆盖度诊断」：有/缺/薄/断链四态——断链指「有道无术」「有术无器」等某层下挂空；**缺层不补造**——标"缺"并记入残留盲区，绝不凭空编一个"道"；仅用户明确要求补齐时才标 `needs_human` 请人工补。薄层/薄链（极少或低置信）提示降权或补源。
- **双向逻辑（关键）**：
  - **正向构建（学：自上而下）**：蒸馏时对来源按 道→法→术→器→细节 收敛——"为什么→用什么方法→什么技法→什么工具→什么参数"，保证技能有原则锚定，而非一堆散碎步骤。
  - **逆向运用（用：自下而上）**：封装出的子技能，**工作流默认按 细节→器→术→法→道 组织**——先落到细节/参数（细节），再识别场景/输入/工具（器），再选技法（术），再套规则/流程（法），最后对原则与边界校验（道）。每一步**向上校验**：细节须落于器、用器必配术、术须合于法、法须合于道。即"逆向逻辑、正向运用"：执行从最细的"细节"出发，却始终朝"道"收敛，不跑偏。
- **结构/导图/流通支撑**：`structure` 抽目录→章节→小标题层级树（**原文物理结构**，含现代别称 aliases）；`dftq` 抽道法术器层级树（**逻辑层级**）；两者维度不同可并存。`mindmap` 由 structure+dftq+relations 派生导图（仅长文生成）；`flows` 显式记录正向推导链与逆向运用链的触发条件与衔接点，直接喂给第 4 步的逆向工作流骨架。
- **示例**：客服技能 = 道（客户第一、绝不夸大承诺）→ 法（1h 内回复／账单升级财务）→ 术（镜像措辞／给替代方案）→ 器（CRM 话术库／工单系统）→ 细节（话术模板四字段：称呼/痛点/替代/收口）。运行从"填哪个模板字段"起，逐步向上校验到"是否守住客户第一"。

> 注：道法术器是**层级框架**而非强制清单；能否抽取到五层、每层是否满链取决于资料本身，诊断结果（有/缺/薄/断链）应如实反映，而非为凑齐而杜撰。

## 12. 领域抽取字段与预设模板（Domain Extension & Presets）
适用：领域特有知识——合规条款、错误码、接口参数、症状→病因——通用五层桶装不下、但对技能质量至关重要时，用 `domain_ext` 桶承载。**不用领域字段的资料不填此桶**。

- **字段语义**（每条 `{ext_type, name, value, applies_when, constraint, dftq_ref, dim, path, confidence, source_ref}`）：
  - `compliance` 合规条款：`name` 条款名 / `value` 条款要点 / `applies_when` 适用情形 / `constraint` 罚则或豁免边界；
  - `error_code` 错误码：`name` 错误码 / `value` 含义 / `applies_when` 触发条件 / `constraint` 处理动作（如 `E1001 额度不足 → 提示充值，不静默重试`）；
  - `api_param` 接口参数：`name` 参数名 / `value` 类型与默认值 / `applies_when` 所属接口 / `constraint` 必填、枚举、正则校验；
  - `symptom_cause` 症状→病因：`name` 现象 / `value` 病因 / `applies_when` 出现场景 / `constraint` 排除法与危险信号（先查危险，再查常见）。
- **领域预设**（第 1 步识别领域后按表启用；`escalation` 升级规则归 `other`；新领域可把 `other` 细化为具名类型，如 `tax_item` / `logistics_status` / `contraindication`）：

| 领域 | 启用 ext_type | 挂接 dim | 对应通用桶 |
|---|---|---|---|
| 客服 / 售后 | compliance、escalation(other) | fa / shu | decisions、edge_cases |
| 合规 / 法务 / 风控 | compliance | fa / dao | rules、ambiguity |
| 代码 / API / 运维 | api_param、error_code | detail / qi | metrics、steps |
| 排障 / 医疗 / 诊断 | symptom_cause | shu / detail | decisions、edge_cases |
| 财税 / 会计 | other(tax_item 税目/税率/申报期) | detail / fa | metrics、rules |
| 电商 / 交易 | other(logistics_status 物流状态)、compliance | shu / fa | state_machine、edge_cases |
| 医疗 / 用药 | symptom_cause、other(contraindication 禁忌) | shu / dao | diagnosis、rules |
| 教育 / 培训 | other(learning_path 学习路径)、deps | fa / detail | deps、steps |

- **落盘**：领域明细通常进子技能的 `references/`（按需加载，如参数表、错误码表、条款清单）；SKILL.md 只保留执行时必读的判断（如"合规红线：绝不经手资金"）。
- 与横向五层的关系：`domain_ext` 是**第七类桶**，与前六层（事实/规则/素材/风格/盲区/结构树）并列；`dftq_ref` 仍把每条领域知识挂回层级树，保证不脱轴。

## 13. 跨次续抽与合并（Incremental Merge）
适用：路径①「暂不补充/记忆暂存」之后，用户追加新资料，把多次抽取累积成一份更完整的技能；也适用多批知识库增量同步。
- **触发**：用户提供新来源并指示「续抽 / 合并 / 追加到已有技能」。
- **流程四步**（与 SKILL.md 路径①的「跨次合并四步」一致）：
  1. **归一化**：新老节点 `title` 去空白/标点/繁简归一化，形成可比键；
  2. **精确合并**：归一后 `title` 相同 → 合并，`summary`/`detail` 取更详尽者，`confidence` 取高者，`source_ref` 追加新来源；
  3. **同义合并**：title 不同但 `summary` 语义等价 → 保留规范名，旧名入 `aliases`；模糊项标 `needs_human`；
  4. **补挂与裁决**：新节点按 `parent_id`+`dim` 补挂到已存树（作为新子项）；同层同名内容冲突走「权威等级 × 置信加权」裁决，记「冲突点/采用/舍弃/理由」四元组。
- **相似度阈值**：语义相似度 ≥0.85 自动合并；0.6–0.85 属模糊项，标 `needs_human` 人工确认，**不自动合并**；<0.6 视为不同节点，作为新子项补挂。`title` 归一相同则必合并（最高优先级）。
- **相似度实现口径**（可执行建议）：①`title` 用归一化后**精确相等**判定（字符级，最高优先级）；②`summary` 先做「字符 n-gram Jaccard」粗筛（≥0.6 进入候选），候选再交 LLM 判语义等价（输出 0–1 相似度）按阈值落定；③无 LLM 时降级用「编辑距离 + 关键词命中」近似（`1 - Levenshtein/len`），并把 0.7–0.85 区间的自动合并降级为 `needs_human`——宁可多审不漏并。
- **合并清单**：每次合并输出四类明细——「合并了谁（old→new）/ 新增了谁 / 补挂到了哪 / 待人工确认」——随后重新跑五层诊断。
- **防膨胀**：合并后节点数超过单次提示舒适区（无法在两页内概括）→ 提示升级路由 B（骨架 + 检索），避免 SKILL.md 无限膨胀。

## 14. few-shot 与逆向工作流映射（Few-Shot × Reverse Flow）
适用：第 4 步封装时，让 few-shot 示例与逆向运用链（细节→器→术→法→道）互为表里——示例既是少样本示范，又是工作流的活演示。
- **三段式结构**：每个示例 = 输入（场景 + 细节）→ 推理（`[器][术][法][道]` 标注）→ 输出（收敛于道）。
- **标注示例**：
  ```
  输入：客户问"你们到底有没有货？"（语气激动）
  推理：[细节] 用户原话"有没有货"，情绪激动；
        [器] 调 CRM 话术模板·库存类；
        [术] 镜像措辞开场："我理解您急着要货"；
        [法] 1 小时内回复；不承诺无依据的库存；
        [道] 客户第一、绝不夸大承诺 → 校验：交期有依据吗？无则不承诺。
  输出：先共情，再给可核实的库存状态与替代方案。
  ```
- **为什么这样组织**：①示例给模型一致格式（few-shot 本职）；②`[器][术][法][道]` 标注直接取自 `flows.reverse` 的 from_dim→to_dim 链，读者照示例就把逆向工作流跑了一遍；③每步向上校验（细节须落于器、用器必配术、术须合于法、法须合于道）显式可见，降低跑偏。
- **数量与选择**：2–4 个示例，覆盖 典型（顺链）→ 边界（断链/缺层如何处理）→ 反例（触犯道的坏输出），让示例集本身构成工作流的完整演示。

## 15. 可选抽取维度：触达 / 条件 / 验收（Optional Extension Buckets）
适用：让蒸馏出的技能「会被正确调用、能走流程、可验证质量」。三组桶**按资料类型启用，不用不填**（与 domain_ext 同原则），全部仍带 `dftq_ref`/`dim`/`path`/`confidence`/`source_ref`，同轴挂回层级树。

- **`triggers`（触达 · 触发与意图）**：`intent` 意图名 / `patterns` 触发说法与关键词（用户怎么说该用）/ `negative` 否定触发（怎么说绝不该用）/ `route_to` 路由目标（多技能竞争时指向谁）/ `priority` 优先级。
  - 客服示例：`intent: 退货咨询，patterns: ["可以退货吗","怎么退","七天无理由"], negative: ["退款到账了吗","投诉"], route_to: 退货流程, priority: 1`——「退款到账了吗」是退款查询不是退货，靠 negative 拦住路由。
  - 下游：子技能「何时使用」段 + description 触发场景 + 路由判断。**几乎所有技能建议抽**。
- **`conditions`（适用条件）**：`type` 三态——`pre` 前置条件（执行前必须满足）/ `post` 后置条件（执行后保证）/ `env` 环境适用（平台/版本/区域/受众矩阵），`applies_to` 指向步骤 order 或规则 id。
  - 示例：`pre: 已登录且有导出权限, applies_to: step-3`；`env: 仅企业版支持私有化部署`。
- **`state_machine`（状态机）**：`state` 当前态 / `event` 事件 / `action` 动作 / `next_state` 下一态 / `guard` 守卫条件——订单、工单、审批、审核类资料的迁移表。
  - 审批示例：`state: 待审批, event: 通过, action: 通知财务入账, next_state: 已通过, guard: 金额≤10万`；`event: 驳回 → next_state: 已驳回`。
  - 下游：子技能状态分支逻辑（同一对象在不同状态走不同分支）。
- **`acceptance`（验收 · 断言与反例）**：`target` 验收对象（规则 id / 步骤 order / dftq 节点）/ `assert` 验收断言 / `pass_condition` 通过条件 / `trap_case` 陷阱题/反例 / `gold_ref` 关联 gold 条目。
  - 示例：`target: r1(7天无理由), assert: "回答须含'7天'且不含'定制商品可退'", pass_condition: "同时满足", trap_case: "客户问定制商品能不能退——必须答不能"`。
  - **与第 5 步打通**：gold 条目直接由 `assert` 生成（question=场景、expected=断言），抽取阶段就把验收标准定下来，验证阶段复用，形成闭环。

**启用建议表**：
| 资料类型 | 建议启用 |
|---|---|
| 简单 FAQ | triggers |
| 流程 / SOP / 审批 / 工单 | triggers + conditions + state_machine |
| API / 接口文档 | triggers + conditions(env) + acceptance |
| 排障 / 诊断手册 | triggers + acceptance |
| 合规 / 风控 / 医疗 | triggers + conditions(env) + acceptance |

**与既有矩阵的关系**：`triggers` 常挂 `cross`（跨层入口）或 `dao`（"什么情况绝不出手"也是原则）；`state_machine`/`conditions` 挂 `fa`（规则与流程层）；`acceptance` 挂 `fa`（规则断言）或 `detail`（参数级校验）。它们不是新主结构，而是给既有桶补充"调用侧/运行侧/验收侧"信息。

## 16. 补充扩展桶：契约 / 推理树 / 生命周期 / 治理（More Optional Extension Buckets）
适用：把 v2.4/v2.5 补全的其余四组可选桶补齐——让蒸馏出的技能「能接外部接口、能走复杂决策、能标注时效与依赖、能守住安全边界」。它们同样**按资料类型启用、不用不填、同轴挂树**（全部带 `dftq_ref`/`dim`/`path`/`confidence`/`source_ref`），与 domain_ext 同原则。

- **`io_contract`（输入/输出契约）**：深化 steps 的"输入/工具"——`step_ref` 指向步骤 order / `input_schema` 入参格式（字段/类型/必填）/ `output_schema` 出参格式 / `failure_mode` 失败返回。
  - API 示例：`step_ref: step-2, input_schema: {order_id: string, required: true}, output_schema: {status: enum[...], tracking: string}, failure_mode: {code:"E4001", msg:"无效单号"}`。
  - 下游：子技能「入参校验」与「出参模板」段，以及脚本类技能的接口文档。**API/接口/脚本类资料建议抽**。

- **`decision_tree`（决策树化）**：把扁平 `decisions` 升为嵌套分支——`node_id` / `question` / `branch`[{`label`,`next`}] / `default` / `weight`（先验概率或优先级）。
  - 排障示例：`node: 报什么错？ → branch[网络错误→查连通性, 权限错误→查 token]`，`default: 收集日志`。
  - 下游：子技能决策分支骨架（比线性 if-else 更贴近诊断/客服分流）。

- **`diagnosis`（诊断树）**：诊断类专用——`symptom` 现象 / `candidates`[{`cause`,`prior`(先验概率), `verify`(验证手段)}] / `exclude_order` 排除顺序 / `red_flag` 危险信号（先查危险再查常见）。
  - 医疗示例：`symptom: 胸痛 → candidates[心梗(prior高, verify:心电图), 肌肉拉伤(prior中)]，red_flag: 放射痛→立即排查心梗`。
  - 下游：子技能诊断流程（现象→候选原因带优先级→排除顺序→验证）。

- **`freshness`（时效）**：`checked_at` 上次核验时间 / `valid_until` 有效期 / `superseded_by` 被谁废弃或替代。`dftq_ref` 挂对应节点。
  - 政策示例：`valid_until: 2026-12-31, superseded_by: 新增值税法`。
  - 下游：第 5 步验证时按 `valid_until` 提示过期风险；路由 B 知识库须按此回标更新时间。

- **`deps`（依赖）**：`prereq` 先学/先掌握的节点 id / `blocks` 被其阻塞的节点 / `rel` 关系（prereq/extends/conflicts）。
  - 培训示例：`prereq: [d1], blocks: [s3]`，表示要先懂 d1 才能学 s3。
  - 下游：子技能「学习顺序」或「执行前依赖检查」。

- **`permissions`（治理边界）**：`who` 谁可用 / `auth` 所需授权 / `data_class` 数据分级（PII/内部/公开）/ `guardrail` 不可逾越的安全红线。
  - 合规示例：`who: 授权客服, auth: 工单系统登录, data_class: PII, guardrail: "绝不输出客户身份证号全文"`。
  - 下游：子技能安全边界段 + 第 6 步质量门「是否触及红线」校验。**合规/金融/医疗/企业内部资料建议抽**。

**启用建议补充表**（接第 15 节）：

| 资料类型 | 补充建议启用 |
|---|---|
| API / 接口文档 | io_contract + decision_tree |
| 排障 / 诊断手册 | decision_tree + diagnosis + freshness |
| 政策 / 价格 / 版本类常变 | freshness + deps |
| 培训 / 课程类 | deps + diagnosis |
| 合规 / 风控 / 医疗 / 企业内部 | permissions（+conditions.env + acceptance） |

**与既有矩阵的关系**：`io_contract` 挂 `qi`(工具接口) 或 `detail`；`decision_tree` 挂 `fa`(决策逻辑) 或 `shu`(分流技巧)，`diagnosis` 挂 `shu`；`freshness`/`deps` 挂对应 dftq 节点（不限定横向层，是元信息）；`permissions` 挂 `dao`(原则红线) 或 `fa`。它们仍是给既有桶补充"接口侧/决策侧/时效侧/安全侧"信息，不新增主结构。

## 17. 媒体摄入协议（Media Ingestion Protocol）
适用：第 1 步输入为**视频**（本地文件/链接）或**网址**，以及需要对同一来源**多次收集**的场景。目标：把非文本媒体转换成可与文本同等处理的「标准来源」，进入第 2 步抽取。

- **视频 → 多模态五轨提取**：
  1. **音频轨**：ASR 转录（whisper 级），输出带**词级时间戳**的文本；
  2. **视频轨**：**场景切分**（scene cut detection）后抽关键帧——只在画面变化时抽帧，每个镜头 1–3 帧，**不做均匀抽帧**（口播视频均匀抽帧会得到大量重复画面）；
  3. **字幕轨**（如有 SRT/内嵌）：与 ASR 对齐，校正语音识别错误；
  4. **画面 OCR**：提取 PPT/白板/代码/图表中的文字——字幕转录拿不到的信息通道，对演示/教学类视频是决定性通道；
  5. **元数据**：标题/简介/时长/作者/发布日期（发布日期喂 freshness）。
- **关键帧三级去重**（画面相似不等于信息重复）：
  1. **pHash 感知哈希**——视觉相似度判定；
  2. **直方图差异**——颜色分布突变判定；
  3. **OCR 文本差异**——画面相同但字幕/PPT 文字变了 → **判新帧，不误删**。
  判定规则：视觉相近 + 文本相同 → 去重；视觉相近但文本不同 → 保留。
- **时间轴对齐 → 图文块**：把转录文字、关键帧、OCR 按时间戳切成 N 个**图文块**（每块 = 一段文字 + 该时段关键帧 + 帧内 OCR）。图文块作为最小知识单元进入第 2 步抽取——文字抽规则、图片作视觉证据（可挂 dftq 的 `qi`/`detail`）、OCR 文字并入文本流。检索与蒸馏时可图文互证，消除文字歧义。
- **画面语义描述**（可选增强）：对保留关键帧调用多模态模型生成一句话画面描述（如「白板上推导出 E=mc²」），并入图文块文本流。与 OCR 互补——OCR 拿"写了什么"，描述拿"在讲什么"，对教学/演示类视频价值显著。
- **说话人分离**（可选，访谈/播客类）：用说话人分离工具（如 pyannote）为转录文本分段打 `[说话人A/B]` 标签，蒸馏时按说话人归组，避免把不同人的观点混成一条规则。
- **自动章节分段**（可选，长视频）：场景切分 + 转录聚类（或 LLM 按语义切章）生成章节标题与时间轴，长视频先章节化再蒸馏；章节可直接喂 `structure` 桶，同源更新时按章节做 diff。
- **网址 → 正文提取**：readability 类算法去广告/导航/评论，保留正文；表格/列表/代码块/图片 alt 文本保留；抓取元数据（URL/标题/作者/**发布时间**）。动态页/需登录页无法抓取时，提示用户导出或授权（与在线知识库同处理）。
- **网址 → 内嵌视频探测**（网址含视频时的补充通道）：访问页面后按三级探测是否含视频——
  1. **直链识别**：URL 本身指向视频文件（`.mp4`/`.webm`/`.m3u8` 流）→ 直接作为视频源解析；
  2. **页面结构识别**：HTML 含 `<video>` 标签 / `og:video` / `twitter:player` 元数据 / 播放器 iframe → 提取真实视频源地址（含 m3u8 分片流）；
  3. **平台页面识别**：URL 为视频平台分享页（B站/抖音/YouTube/视频号等）→ 按平台规则解析视频地址。
  探测命中 → 下载/流化后走上方「视频 → 多模态五轨提取」流程（ASR/关键帧/OCR/字幕/元数据 → 图文块），与正文提取结果**合并**为同一来源的多通道输入。平台需登录/反爬/签名校验无法直接抓取时，提示用户下载视频后走本地视频输入；并在 `source_media.note` 标 `platform_video`。
- **媒体来源展开（多视频形态）**：一个链接可能不是单个视频——先判定**来源形态**再展开为视频清单：
  | 形态 | 信号 | 展开动作 |
  |---|---|---|
  | S1 单视频 | URL 直接指向单个视频 | 直接五轨提取 |
  | S2 多视频页 | 页面含多个视频条目（聚合页/图文嵌多视频） | 提取全部视频源 → 逐条摄入 |
  | S3 合集/播放列表 | 平台合集页（playlist/collection 路径特征） | 展开列表内全部视频 |
  | S4 主页/空间 | 博主主页（channel/space/user 路径特征） | 展开全部或裁剪后的视频 |
  | S5 多链接输入 | 用户一次给 N 个链接（可混合形态） | 各自判定形态后合并去重 |
  展开用 yt-dlp 的 `--flat-playlist --print` 预扫列表（秒级，不下载）；**数量管控**：清单超阈值（默认 >20 条）时须用户选择范围——全部 / 最近 N 条 / 指定时间段 / 指定合集 / 关键词过滤；合并清单按视频 id 去重，`source_media` 记 `parent_uri`（来源页）+ `collection` 标注，子视频各自可溯源。展开后的视频清单 → 逐条五轨摄入 → 全部入 `knowledge-grains/` → 统一跨次合并 → 一次压缩（与第 19 节批量编排衔接）。
- **多次收集 → 版本化增量**：
  1. 同源再次摄入时存为新版本 `raw-extract-<source>-<collected_at>.json`，旧版保留（`knowledge-grains/` 只增不改）；
  2. 文本 diff 比对变化部分；
  3. 仅对变化部分走「跨次合并四步」（第 13 节）增量更新 dftq 树；
  4. 变化记录写入 evolution-log（若子 skill 已发布，自动触发升级环）。
- **落点**：`source_ref` 扩展支持 `video_timestamp`（如 `00:12:34`）、`frame_id`、`url`、`collected_at`，与 path 锚点并存；图文块挂 dftq 树时保留媒体溯源，便于 gold 验证回溯到视频具体位置。

## 18. 记忆与双层进化（Memory & Dual-Layer Evolution）
适用：一切希望技能**随资料完善自动升级**的场景；蒸馏工厂自身也据此元进化。完整协议见 references/evolution-protocol.md，本节给要点与判定规则。

- **记忆库**：子 skill 出厂预装 `references/memory/`——`knowledge-grains/`（增量颗粒，只增不改）/ `feedback/`（纠错·失败·缺口）/ `version-state.json`（dftq 快照+版本）/ `evolution-log.md`（版本链）。
- **四类触发器**：①新资料摄入 ②用户纠错 ③gold 失败（使用期通过率 <80%）④freshness 到期。②③ 默认**累积触发**（同类反馈 ≥3 条，或高风险红线反馈 1 条即时触发）。
- **升级环七步**：沉淀记忆 → 增量 diff → 跨次合并 → 重诊断 → 重压缩 → 回归验证 → 版本++ 发布；任一步失败即回滚上一版。
- **回归验证**：升级必须过「旧 gold 回归（通过率 ≥90% 或持平）+ 新 gold 增补」双门；失败回滚并记入 evolution-log，最多 2 轮自我修正，仍失败标 `needs_human`。
- **版本号**：`major.minor.patch`——结构变化（新增道/法/器）→ minor；内容修正 → patch；进化机制变化 → major。
- **工厂层元进化**：学习信号 = 每次蒸馏运行记录 + 用户反馈 + 子 skill failed-cases；沉淀入 `factory-log.md`；每 10 次蒸馏或用户要求时自检改进工厂自身，工厂版本++。
- **铁律**：增量优先（只处理变化部分，不全量重抽）· 回归保护（旧能力不退化）· 可回滚（版本快照 + 历史颗粒）。

## 19. 批量蒸馏编排（Batch Distillation）
适用：一次摄入**多份资料**（多文档 / 多视频 / 多网址 / 混合），流水线地产出或升级技能，而非一份份手工重复。

- **流水线三步**：
  1. **逐份摄入与抽取**：每份来源独立走第 1–2 步（媒体来源走媒体摄入协议），抽取结果全部落入 `knowledge-grains/`（不预先合并，保持每份可溯源）；
  2. **统一跨次合并**：按「跨次合并四步」（第 13 节）把各份颗粒合并为一份 dftq 树——多份之间天然复用多源对齐（去重 / 消歧 / 冲突裁决）；
  3. **一次压缩封装**：对合并后的树统一做五层诊断 → 决策点 → 压缩 → 封装 → 验证 → 输出。
- **与多源模式的区别**：多源模式面向"多个来源融合成一个新技能"；批量编排强调**流水线 + 增量复用**——已有技能时，新批次只对增量部分跑合并与回归验证（增量优先），产出直接触发子 skill 升级环。
- **产出**：一份融合 SKILL.md（按统一能力命名）+ 每份来源的溯源记录 + 合并清单 + 回归验证报告。
- **规模兜底**：批次合并后超出路由 B 判定阈值 → 升级为骨架 + 检索路由，不无限膨胀 SKILL.md。

## 20. 知识库来源与蒸馏（在线 + 本地）
适用：用**知识库**作为蒸馏来源——在线（ima/乐享等）或**本地**（本地文档库 / 目录 / Obsidian vault / 已建本地索引）。知识库蒸馏通常走路由 B（骨架 + 检索）；知识库更新后走 KB Diff 再进化（见 evolution-protocol.md 第 11 节）。

- **在线知识库**：连接器授权 → 检索/获取工具拉取片段 → 文本作为来源（与第 6 节一致）；连接与授权是前提，须明确提示。
- **本地知识库（v3.1 新增支持）**：
  - **形态**：本地目录（批量 md/docx/pdf/epub/txt）、Obsidian vault、已建全文/向量索引（如 ChromaDB / LanceDB / meilisearch）的本地知识库；
  - **摄入**：无需授权——递归扫描支持的格式 → 批量解析为文本（markitdown / pdf 技能）→ 逐份走第 1–2 步抽取 → 全部入 `knowledge-grains/` → 统一跨次合并 → 一次压缩（复用第 19 节批量编排）；
  - **路由**：体量大或常变 → 路由 B（骨架 + 本地检索：可建全文索引如 ripgrep / meilisearch，或向量索引）——检索路由指向本地索引；小且稳定 → 路由 A 全量嵌入；
  - **溯源**：`source_ref` 用 `local-kb/<相对路径>`，在线用 `kb:<库名>`；`source_media.type` 可扩展 `kb`。
- **更新再进化**：在线与本地共用 KB Diff（evolution-protocol 第 11 节）——本地知识库的"重检索"即"目录重扫 + 指纹对比"（文件 mtime / content_hash），新增/删除/修改同样三分处理，只对差异走增量升级。
- **批量蒸馏衔接**：知识库蒸馏天然是"多源批量"——一次摄入多份文档/多个检索片段，产出**一个**融合技能（按能力命名，非按文档）。
