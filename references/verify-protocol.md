# Gold 验证协议（第 5 步实操手册）

第 5 步「真验证与迭代闭环」的操作细则：如何构造 gold、如何实跑、如何判定、如何回流。**禁止只在脑中模拟**——必须把草稿技能真实加载后执行。

## 1. 构造 gold 集

- 从来源**自动抽取** 3–5 个真实问答/场景作为金标准；或采用用户指定的测试集。**若第 2 步抽了 `acceptance` 桶，gold 直接由 `acceptance.assert` 生成**（question=场景、expected=断言、checkpoints=pass_condition），不必另造，抽取与验证形成闭环。
- 每条 gold 结构：
  ```
  {"id":"g1","question":"<喂给技能的输入>","expected":"<期望输出要点>","checkpoints":["<判定点1>","<判定点2>"],"path":"<来源锚点，如 /第三章/3.2节>"}
  ```
- 覆盖要求：至少 1 条覆盖「道/法」层原则（边界校验类）、1 条覆盖「术/器」层操作类、1 条覆盖边界 case 或歧义项。**每条 gold 必须有来源锚点**，否则视为臆造测试，不采用。

## 2. 实跑加载（关键：真实加载，不是脑中跑）

- 把草稿技能放入临时目录：`_verify/<skill-name>/SKILL.md`（references/ 等一并放入）。
- 在子 Agent / 沙箱中，按**真实调用方式**加载该 SKILL.md（与生产加载路径一致），逐条喂入 gold 的 `question`，记录**原始输出**（不润色、不代答）。
- 若第 4 步产出的是路由 B 骨架技能，验证时须挂上检索后端（本地索引或在线知识库连接），并记录「是否成功检索」。

## 3. 判定

对每条 gold 输出标注四态之一，并归类失败原因：

| 判定 | 含义 |
|---|---|
| 答对 | 输出覆盖全部 checkpoints，无事实错误 |
| 部分答对 | 覆盖部分 checkpoints，或有次要错误 |
| 答错 | 关键 checkpoints 缺失或事实错误 |
| 答非所问 | 输出偏离问题意图 |

失败原因分类：`缺规则` / `规则含糊` / `冲突未解` / `格式不符` / `检索失败`（仅路由 B）。

记录格式：
```
g1 答对    覆盖：checkpoints 1,2
g2 部分答对 缺「升级到财务」分支 → 原因：缺规则（source: ch3）
```

## 4. 回流修正

- `缺规则`/`规则含糊` → 回第 3 步压缩重提炼；必要时回第 2 步补抽取。
- `冲突未解` → 走冲突裁决（权威×置信）或标 `needs_human`。
- `格式不符` → 回第 4 步改输出模板/few-shot。
- 迭代上限：默认 3 轮。通过率门槛：默认 ≥80%。
- **已知缺失容忍**：用户走决策点路径③（不补充直接封装）时，`known-gaps.md` 中已登记的缺失不计入失败；gold 中与之相关的条目按「预期豁免」处理并注明。

## 5. 输出

第 6 步报告固定包含：
- **gold 通过率**：`答对 + 部分答对×0.5 / 总数`（可配置为仅答对计入）；
- **失败明细**：每条失败 gold 的判定 + 原因 + 来源锚点；
- **回流记录**：第几轮、改了什么、是否达标；
- **待人工审阅优先级**：`low`/`ambiguous`/`assumed`/`needs_human`/合并模糊项，按 confidence 降序。

## 6. 可选脚手架（scripts/run_gold 草案）

若产出技能含 scripts/ 目录，可附一个最小验证脚本（伪代码）：
```
1. 读 draft/SKILL.md + gold.json
2. 为每个 gold 调一次子 Agent（加载该 SKILL.md），拿到输出
3. 按 checkpoints 关键字/规则比对，给出判定
4. 汇总通过率与失败明细，写入 verify-report.md
```
注意：gold 判定涉及语义，脚本只做格式化的「预筛」；最终判定由验证 Agent 人工/LLM 复核，脚本结果仅供参考。

## 7. 扩展桶验证要点

- `acceptance`：gold 由 `assert` 直接生成（见第 1 节），逐条比对输出是否满足 `assert` + `pass_condition`。
- `decision_tree` / `diagnosis`：gold 须覆盖至少一个分支 / 候选原因；判定时检查「选对分支 / 排对因果」，而非只看最终答案。
- `io_contract`：gold 须含一例非法入参（应触发 `failure_mode`）与一例出参格式检查。
- `freshness`：验证前先扫 `valid_until`，已过期节点在报告中标「时效预警」，不计入失败但须提示重蒸馏。
- `permissions`：gold 须含一例触碰 `guardrail` 的边界（如"输出客户身份证号"应被拒绝）；触红线视为「违规」，直接判失败并标 `needs_human`。
- `state_machine`：gold 须覆盖一个状态迁移（事件→动作→下一态），判定动作与 `next_state` 是否正确。

## 8. 升级回归验证（v3.0：子 skill 自动进化时的验证）

当子 skill 进入自动进化（见 evolution-protocol.md），第 5 步验证升级为**回归验证**：
- **旧 gold 回归**：升级前的 gold 集全部重跑，通过率不得低于升级前基线（默认 ≥90% 或持平）——防"修了这个坏了那个"；
- **新 gold 增补**：本次变更对应的新断言（来自纠错 / 失败案例 / 新资料）全部通过；
- 任一不通过 → **回滚上一版**（从 knowledge-grains 历史 + version-state 快照恢复），失败原因记入 evolution-log.md；
- 允许最多 2 轮自我修正（重提炼 → 再验证）；仍失败标 `needs_human` 进入人工审阅。
- 媒体来源（视频/网址）的 gold 断言可引用 `source_ref` 的 `video_timestamp` / `frame_id`，判定时回溯到视频具体片段核验。
