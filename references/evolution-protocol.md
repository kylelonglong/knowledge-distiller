# 记忆与自动进化协议（Evolution Protocol · v3.0）

让蒸馏出的子 skill「出厂即带进化能力」：随着资料不断完善、用户反馈累积、验证失败暴露、知识过期，技能自动升级而非重做；蒸馏工厂自身也据此元进化。核心铁律：**增量优先 · 回归保护 · 可回滚**。

## 1. 记忆库结构（子 skill 出厂预装）

每个蒸馏产出的子 skill 发布时，同步建立 `references/memory/` 目录：

```
skill-name/
└── references/
    └── memory/
        ├── knowledge-grains/          # 知识颗粒库（增量摄取，只增不改）
        │   ├── raw-extract-<source>-<timestamp>.json   # 每次第2步的完整中间表示
        │   └── media-chunks/          # 视频/网址来源的图文块与提取元数据（如适用）
        ├── feedback/                  # 使用期反馈池
        │   ├── corrections.md         # 用户纠错（旧答案 / 正确答案 / 依据）
        │   ├── failed-cases.md        # gold 失败案例（输入 / 输出 / 期望 / 失败原因）
        │   ├── gap-notes.md           # 使用中发现的缺口（缺层/断链/新场景）
        │   └── factory-feedback.json  # 机制/宿主类反馈（v3.7 新增，推模式自动生成，见 §14）
        ├── version-state.json         # 当前版本状态（dftq 树快照 / 版本号 / 覆盖率 / 置信度基线）
        └── evolution-log.md           # 进化日志（每次升级一行：触发 → 变更 → 验证 → 版本）
```

**写库规则**：
- `knowledge-grains/` 只增不改——历史颗粒是回滚与回归验证的素材，绝不被覆盖。
- 反馈池每条记录带 `timestamp` + `trigger` 来源（correction / failed-case / gap）。
- `version-state.json` 是唯一可变文件，每次版本发布后更新快照。

## 2. 四类进化触发器

| 触发器 | 信号来源 | 典型场景 | 处理 |
|---|---|---|---|
| ① 新资料摄入 | 用户追加文档/视频/网址/问答 | "这份资料也加进技能"、"再收集一次这个网页" | 增量抽取 → 跨次合并 → 升级 |
| ② 用户反馈纠错 | `feedback/corrections.md` | "上次回答错了，正确的是…" | 纠错入记忆 → 触发规则修订 → 升级 |
| ③ gold 验证失败 | `feedback/failed-cases.md` | 使用期实测通过率 < 门槛（默认 <80%） | 失败案例入记忆 → 回流重提炼 → 升级 |
| ④ freshness 到期 | `freshness.valid_until` 过期 | 政策/价格/版本类知识过期 | 提示重检 → 重抽该源 → 升级 |

触发策略：②③ 支持两种模式——**即时升级**（用户明确要求"现在就改"）或**累积升级**（默认：同类反馈 ≥3 条或任一高风险红线反馈 1 条时触发一次）。

## 3. 升级环（七步，增量优先）

```
触发 → ① 沉淀记忆（信号入 knowledge-grains/ 或 feedback/）
     → ② 增量 diff（对比新颗粒 vs version-state 快照，只取变化部分）
     → ③ 跨次合并（复用「跨次合并四步」：归一化→精确→同义→补挂裁决）
     → ④ 重诊断（五层覆盖度诊断，缺口入 known-gaps）
     → ⑤ 重压缩（以合并后的 dftq 树重写规则/步骤/few-shot）
     → ⑥ 回归验证（旧 gold + 新 gold 全部实跑，见第 4 节）
     → ⑦ 版本++ 发布（更新 version-state.json + evolution-log.md，保留旧版本可回滚）
```

**增量原则**：只处理变化部分——新增节点补挂、变更节点替换、失效节点标记 `superseded`；未变的节点与示例不重写，避免全量重抽引入回归。

## 4. 回归验证（防"修了这个坏了那个"）

升级必须通过双重验证才算成功：
- **旧 gold 回归**：升级前的 gold 集全部重跑，通过率不得低于升级前基线（默认 ≥90% 或持平）；
- **新 gold 增补**：本次变更对应的新断言（来自纠错/失败案例/新资料）全部通过。
- 任一不通过 → 本次升级**回滚到上一个版本**（从知识颗粒历史 + version-state 快照恢复），失败原因记入 evolution-log.md，供下次升级规避。
- 升级环允许最多 2 轮自我修正（重提炼 → 再验证）；仍失败则标记 `needs_human` 进入人工审阅。

## 5. 版本管理与回滚

- 版本号：`major.minor.patch`——新资料导致结构变化（新增道/法/器）→ minor；仅修正/更新内容 → patch；进化机制本身变化 → major。
- 每次发布：更新 `version-state.json`（dftq 快照 + 版本号 + 覆盖率 + **gold 集快照**）+ `evolution-log.md` 追加一行。gold 集快照也可存 `knowledge-grains/gold-sets/<version>.json`——回归验证的「旧 gold」从这里取，不依赖记忆。
- 回滚路径：读上一版 `knowledge-grains/` 中的全量颗粒 → 重跑合并到上一版快照 → 恢复到上一版 SKILL.md（CHANGELOG 记录回滚原因）。

## 6. 双层进化

**子 skill 层（自动进化）**：出厂预装上述记忆库 + 升级环，四类触发器自动驱动。

**工厂层（元进化）**：蒸馏工厂自身积累学习信号并自我改进——
- 学习信号：每次蒸馏的运行记录（来源类型/抽取诊断/决策点选择/验证报告/落盘清单）+ 用户对产出的反馈 + 子 skill 使用期 failed-cases 回流 + **子 skill 运行期 mechanism 类反馈（v3.7 新增，经 §14 回传通道收集）**。
- 沉淀：每次蒸馏后向 `references/factory-log.md` 追加一条**结构化记录**（Markdown 表或 JSON 行）：
  `{date, source_type(文档|视频|网址|知识库), 踩坑, 失败模式(可选：缺规则/冲突/断链/验证不过), 用户反馈, 可改进点, 状态(pending|adopted)}`——`adopted` 表示该改进已固化进工厂（如新增领域预设、修正规则、补工具装配）。
- 升级触发：积累到阈值（默认每 10 次蒸馏）或用户主动要求时，蒸馏器自检自身 SKILL.md / 方法文档 / 模式库，把重复出现的失败模式固化为规则，工厂版本++（CHANGELOG 记录）。**v3.7 新增**：子技能运行期 mechanism 类反馈累积同类 ≥3 条（默认）也触发一次工厂自检（详见 §14）。
- **元进化闭环**：工厂 → 子 skill（带进化机制出生）→ 子 skill 反馈（内容类：自身升级；机制/宿主类：回传工厂）→ 改进工厂 → 产出更好的子 skill。完整回传通道见 §14。

## 7. 与既有机制的关系

- **决策点路径①**（暂存记忆）：用户侧被动触发的"等资料"机制，产物是 `raw-extract-*.json`（staged）；记忆板块把该产物也纳入 `knowledge-grains/`，与主动进化共用同一颗粒库。
- **跨次合并（第 13 节）**：升级环第 ③ 步直接复用其四步流程与相似度阈值（≥0.6 自动合并：≥0.85 高置信 / 0.6–0.85 中置信入待验证清单；<0.6 补挂；title 归一相同必合并）。合并纠错靠**验证驱动降级**（§13.1）：合并点被 gold 失败归因 ≥2 轮 → 拆分回滚 + 转 needs_human + 阈值降档。
- **freshness 桶**：触发器④的判据来源；freshness 过期时升级环会重抽该源。
- **第 5 步真验证**：升级环第 ⑥ 步是其"使用期版本"——第 5 步验证的是发布前，回归验证覆盖发布后。

## 8. 默认参数表（集中配置，按需调整）

| 参数 | 默认值 | 说明 |
|---|---|---|
| 升级环最大轮数 | 2 轮 | 自我修正上限，超出标 `needs_human` |
| 回归旧 gold 门槛 | ≥90% 或持平 | 防能力退化（第 4 节） |
| gold 通过率门槛（使用期） | <80% 触发升级 | 触发器③判据 |
| 同类反馈累积阈值 | ≥3 条 | 触发器②累积模式 |
| 高风险红线反馈 | 1 条即触发 | 触发器②即时模式 |
| 工厂升级蒸馏次数 | 10 次 | 工厂层升级触发 |
| 机制类反馈累积阈值 | ≥3 条（同类） | 子技能运行期 mechanism 反馈触发工厂自检（§14） |
| 低风险机制类修复 | 默认自动 | 不触碰抽取矩阵/Schema/协议；自动应用 + 回归验证 + 可回滚（§14） |
| 高风险机制类修复 | 默认人工确认 | 触碰抽取矩阵/Schema/协议；自动归因+建议，落地需用户确认（§14） |
| 覆盖率不足回流阈值 | <70% | 第 3 步回流判据 |
| 跨次合并相似度 | ≥0.6 自动（≥0.85 高置信 / 0.6–0.85 中置信入待验证）；<0.6 补挂 | distillation-method 第 13 节 |
| 合并降级触发 | 同一合并点被 gold 失败归因 ≥2 轮 | distillation-method §13.1 |

## 9. 反馈写入时机与线上回测（调用约定）

- **谁写反馈**：子 skill 使用方（用户 / 调用 AI / 宿主）在以下时机写入——
  - 用户明确纠错 → `feedback/corrections.md`（旧答案 / 正确答案 / 依据）；
  - 实测输出判定失败 → `feedback/failed-cases.md`（输入 / 输出 / 期望 / 失败原因）；
  - 使用中遇到未覆盖场景 → `feedback/gap-notes.md`（场景 / 期望 / 缺口）。
- **线上回测**（触发器③的数据来源）：建议定期（默认每月一次）把当前 gold 集在真实使用环境重跑（或抽样最近 N 次真实对话），通过率 <80% → 触发升级环；线上回测可复用 `scripts/run_gold.py`（results.json → 判定 → 报告）。
- **gold 集快照**：每次发布把当时的 gold 集写入 `version-state.json`（`gold_snapshot`）或 `knowledge-grains/gold-sets/<version>.json`——回归验证的"旧 gold"从这里取，不依赖记忆。

## 10. 路由 B（RAG）技能的进化

- **骨架技能**：升级环照常（新增稳定规则 / 判断流程 → 版本++）。
- **检索侧**：`freshness` 到期或新资料摄入时，**更新检索路由与索引约定**（知识库名/id 变更、检索词更新），并重跑「检索成功率」gold（挂检索后端实跑）。
- **进化信号**：路由 B 技能的使用期反馈重点记录「检索失败」（failed-cases 里单列 `检索失败` 原因），累积 ≥3 条 → 触发检索路由修订。

## 11. 知识库技能再进化（KB Diff：变更检测 + 骨架重估）

适用：用**知识库**（在线 ima/乐享，或本地文档库/索引，见 distillation-method 第 20 节）蒸馏出的子 skill，知识库后期更新时如何再次进化。核心：**主动检测变更，只对差异做增量升级**。

- **检索范围快照（kb_snapshot）**：首次蒸馏知识库时，把"检索范围"固化进 `version-state.json`：
  - `kb_snapshot = {库类型: online|local, 库名/路径, 范围列表: [检索词/目录id/文件清单], 片段指纹: [{片段key, content_hash}], 探针查询: [...], checked_at}`；
  - 指纹用内容 hash（如 sha256 前 16 位）——片段级对比，比全文 diff 快。
- **触发途径**（任一路径即启动 KB Diff）：
  1. freshness 到期（`valid_until` / `update_freq` 到点）；
  2. 用户告知（"知识库更新了，重新进化一下"）；
  3. 定期轮询（可选，用 automation 按周/月跑一遍重检）；
  4. 在线知识库若有 API 变更通知 → 订阅事件（未来扩展）。
- **KB Diff 流程**：
  1. 按 `kb_snapshot.范围列表` 重新检索/扫描同一范围；
  2. 逐片段计算指纹，与快照对比，分为三类：
     - **新增**（旧快照无）→ 增量抽取 → 补挂到 dftq 树（走跨次合并四步）；
     - **删除**（快照有、现在无）→ 对应节点标 `superseded`，**检查依赖**（deps 中被删节点阻塞的链要重连）；
     - **修改**（指纹不同）→ 重抽该片段 → 替换对应节点（`confidence` 重估，`source_ref` 更新为最新检索时间）。
  3. 只对差异片段走「增量抽取 → 跨次合并 → 回归验证 → 版本++」，未变的片段不动。
- **骨架规则 freshness 重估**（补缺口）：路由 B 骨架里的"稳定规则"若标注了来源（`kb_ref`），KB Diff 后逐条核对——规则是否仍被最新检索支持：支持 → 保留；已变 → 更新骨架规则（bump minor）；已被删除/矛盾 → 移除或标 `needs_human`。骨架规则的 `kb_ref` 标注在封装时写入。
- **检索质量对比**（可选）：KB Diff 时同时跑一组固定探针查询（`kb_snapshot.探针`），对比新旧命中率/召回率；显著下降（>20%）→ 提示知识库结构调整（条目改名/文档移动），触发检索路由与索引约定修订。
- **与第 10 节的关系**：第 10 节是"骨架技能自身的进化"（被动信号）；本节是"知识库源变更驱动"的**主动检测**——两者配合：KB Diff 发现检索路由失效时交给第 10 节处理。

## 12. 再进化模式（把现有子 skill 当来源重新蒸馏 · v3.2 新增）

第 1–6 步是「从零蒸馏」：输入原始资料，产出 v1.0.0 子 skill。当目标是**升级一个已存在的子 skill** 时，应走本模式——**把现有子 skill 本身（SKILL.md + 它的 `references/memory/`）当作来源**，叠加新的进化信号，跑增量升级环，而不是从零重抽。SKILL.md「再进化模式」段为本模式的入口与速查。

**输入（三要素）**：
- 现有子 skill：`SKILL.md` + `references/memory/`（`version-state.json` 快照 + `knowledge-grains/` 历史颗粒 + gold 集快照 + `evolution-log.md`）；
- 新信号（四选一或组合）：①新资料（文档/视频/网址/问答）②用户纠错（`corrections.md`）③知识库更新（KB Diff，见 §11）④freshness 到期（重抽该源）；
- 可选：用户指定的变更范围 / 仅跑回归验证。

**流程**（复用升级环，非从零）：
1. 载入：读 `version-state.json`（现有 dftq 快照 + 版本号 + 覆盖率/置信度基线 + gold 快照）；读 `knowledge-grains/` 历史颗粒（回归与回滚素材）。
2. 信号入记：新资料 → 第 1–2 步抽取为 `raw-extract-<source>-<ts>.json` 入 `knowledge-grains/`；纠错 → `feedback/corrections.md`；KB 更新 → 走 §11；freshness → 标 `freshness.valid_until` 过期。
3. 跑升级环（§3 七步）：增量 diff（新颗粒 vs 快照）→ 跨次合并 → 重诊断 → 重压缩（**仅重写变化部分**，未变节点/示例不动）→ 回归验证（旧 gold + 新 gold 全过）→ 版本++（结构变 bump minor / 仅更新内容 bump patch）→ 更新 `version-state.json` + `evolution-log.md`，保留旧版可回滚。
4. 输出：新版本 `SKILL.md` + 更新后的 `references/memory/`。

**与从零蒸馏的关键区别**：加载现有 memory、增量升级、不重跑全量压缩；版本号从现有 `version-state.json` 续推，而非从 v1.0.0 起。

**不要求写回工厂**：本模式的目标子 skill 可以位于任意位置——用户级 `~/.workbuddy/skills/`、项目级 `.workbuddy/skills/`、或任意目录——只要它携带 `references/memory/`，就能被本工厂再进化。这与「把发现工厂自身的改进缺口写回本技能」是**正交**的两件事（详见 SKILL.md「再进化模式」段与项目约定"工厂技能改写回惯例：用户决定制，默认不动"）。

## 13. 独立子 skill 的触发器监控（手动 vs 自动边界 · v3.2 新增）

四类触发器（§2）中，哪些能"自动"触发，取决于子 skill 是否接入了运行期监控。明确边界，避免"独立进化"与"写回工厂"被混淆：

| 触发器 | 信号来源 | 独立子 skill（未挂监控） | 接入监控后 |
|---|---|---|---|
| ① 新资料摄入 | 用户主动追加 | ✅ 天然用户驱动（用户给资料即触发） | 同左 |
| ② 用户纠错 | `corrections.md` | ✅ 天然用户驱动（用户纠错即触发） | 同左 |
| ③ gold 验证失败 | `failed-cases` / 线上回测 | ⚠️ **手动**：需用户/调用方说"重新验证/进化这个 skill"，或手动跑 `scripts/run_gold.py` 回测 | ✅ 可 automation 定期（默认每月）跑线上回测，<80% 自动触发 |
| ④ freshness 到期 | `freshness.valid_until` | ⚠️ **手动**：需用户说"KB/资料更新了，重新进化" | ✅ 可 automation 按 `update_freq` 定期轮询（见 §11 触发途径 3） |

**推荐默认**：独立子 skill 保持**手动触发**——①②用户驱动本就手动；③④由用户在有更新/过期迹象时主动发起再进化。这能保持「写回工厂 vs 独立进化」的边界清晰：子 skill 不依赖工厂常驻监控也能进化，只需在任何时刻把它（含 `references/memory/`）喂回工厂即可（走 §12 再进化模式）。

**真·自动（可选）**：若希望 ③④ 也自动，把子 skill 的 `evolution-log.md` 挂到 automation（如每月跑一次 KB Diff / gold 回测），或把子 skill 注册进工厂监控清单。但这会引入「独立子 skill ↔ 工厂」的常驻耦合，与"不强制写回工厂"取向略有张力——**仅在用户明确要自动时才启用，且默认不开启**。

**与 §14 的衔接（v3.7 新增）**：无论子 skill 是手动还是自动触发升级，升级环执行时都要顺带做一次「反馈分诊」——内容类问题走自身升级（本协议 §3），机制/宿主类问题**自动生成 `feedback/factory-feedback.json`（推模式）**，供工厂下次调用时拉取（§14）。这一步不改变"子 skill 不依赖工厂常驻监控也能进化"的取向——推/拉都发生在"子 skill 跑升级环"或"工厂被调用"这两个天然时点，无需常驻进程。

## 14. 子技能运行期反馈回传与工厂自动归因（v3.7 新增）

适用：**子技能在真实使用中遇到"自己解决不了的问题"时，把信号回传给主技能（工厂），由工厂归因并自动/受控地优化自身产出**。补上"元进化闭环"缺失的那半截：之前只有"子技能内容类反馈 → 自身升级"（§3），没有"机制/宿主类反馈 → 回传工厂"的通道。

### 14.1 三类问题分诊（回传前先归因）

子技能运行期问题按根源分三类，**决定走哪条处理路径**：

| 类型 | 判定要点 | 处理路径 |
|---|---|---|
| **content（内容类）** | 改子技能自身的规则/知识/示例就能修（答错、过时、缺场景） | 子技能走升级环（§3），**不回传工厂** |
| **mechanism（机制类）** | 改子技能内容修不了，只有改**工厂的产出逻辑**才能修（SKILL.md 结构缺字段、schema 不兼容、脚本报错、few-shot 指引导致调用方行为错误） | **回传工厂** → 进工厂待办 → 按 §14.3 修复 |
| **host（宿主类）** | 换环境/重启/授权/换工具集就能解（沙箱通道故障、权限、网络、连接器未授权） | **不回传工厂作为"工厂缺陷"**——生成宿主 Bug Report 模板交用户上报宿主；与 §17.1 C 类同判 |

**归因辅助规则**：能通过"给子技能补一条规则/示例"解决 → content；必须改"工厂下次怎么蒸馏"才能根治 → mechanism；问题在工具/环境而非知识或产出 → host。**机制类与宿主类易混淆**——先排除宿主（重启/授权/换通道是否解决），再判机制。

### 14.2 回传通道（双通道 + 手动兜底）

- **推模式（子技能侧）**：子技能升级环执行时（§3/§12），对本次处理的反馈做分诊；mechanism/host 类（host 仅记录备查）自动写入 `references/memory/feedback/factory-feedback.json`：
  ```json
  {
    "id": "ff-001",
    "skill": "skill-name",
    "version": "1.2.0",
    "date": "2026-08-26T09:00+08:00",
    "symptom": "运行报错：...",
    "cause_type": "mechanism",          // mechanism | host
    "self_resolved": false,             // 子技能升级环是否已尝试解决
    "detail": "子技能 SKILL.md 缺 X 字段导致调用方无法解析",
    "gap_ref": "failed-cases.md#20260826-01"
  }
  ```
- **拉模式（工厂侧）**：工厂每次被调用（蒸馏 / 再进化 / 批量）时，**可选扫描**用户指定范围（如 `~/.workbuddy/skills/`、项目 `.workbuddy/skills/`，或用户声明的目录）内各子技能的 `feedback/factory-feedback.json`；未读条目（按 `id` 去重）汇入工厂 `references/factory-log.md`（`status: pending`），并记录已读 id 避免重复处理。**扫描前先问用户**"是否收集已发布子技能的机制类反馈"，不静默扫描用户磁盘。
- **手动兜底**：用户直接把子技能（含 `references/memory/`）喂回工厂走再进化（§12），或粘贴反馈文本——工厂同样按 §14.1 分诊。

### 14.3 工厂侧自动修复边界（低风险自动 / 高风险人工）

机制类反馈汇入 `factory-log.md` 后，同类累积 **≥3 条（默认）** 触发一次工厂自检（也可由用户主动触发）。自检产出「改进建议清单」，按风险分级落地：

- **低风险机制类**（补字段 / 补示例 / 改文案 / 修文档笔误 / 补工具命令——**不触碰抽取矩阵与 Schema**）：工厂可**自动应用**修复 → 跑回归护栏（两路径 `quick_validate.py` 均 "Skill is valid!" + `py_compile` 全过 + 旧功能抽查）→ 通过则工厂版本 `patch++` 并记 `adopted`；失败即回滚并记回 factory-log，转人工。
- **高风险机制类**（改抽取矩阵 / 改 Schema / 改进化协议 / 改媒体协议 / 加领域预设）：工厂**只自动归因 + 生成改进建议**，实际落地需用户明确确认（遵循项目约定「工厂技能改写回惯例：用户决定制，默认不动」）。用户确认后按 `minor++` 升版发布。
- **宿主类**：不进入工厂待办；输出「宿主 Bug Report 模板」（现象 / 复现步骤 / 环境 / 已试措施 / 期望行为）交用户上报宿主，`factory-log` 仅记一条 `host_reported` 备查。

**回归护栏（低风险自动修必须过）**：① 两路径 `quick_validate.py` 均通过；② 全部 `.py` `py_compile` 通过；③ 受影响功能旧样例抽查不回归。任一不过 → 回滚本次修改并标记 `needs_human`。

### 14.4 与既有机制的关系

- **§6 工厂层元进化**：§14 是它的"信号入口"实现——元进化升级触发除"每 10 次蒸馏/用户要求"外，新增"机制类反馈同类 ≥3 条"。
- **§13 触发器监控边界**：推/拉不要求常驻监控（见 §13 衔接段）；若用户给子技能挂了 automation 定期回测，推/拉会更频繁，属自然增强。
- **项目约定「工厂技能改写回惯例」**：本节**不推翻**"用户决定制"——低风险自动修是用户在本版本已确认的授权（AskUserQuestion 拍板），高风险仍人工确认；新用户若未授权，默认回到"仅归因+建议"。
